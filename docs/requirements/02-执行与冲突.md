# 02 · 执行与冲突

> 决策依据：D3（立即执行走手动链路）、D4/D5（多仪器零点新类型、每台一条记录）、D10（三类触发被拒都写记录）、D11（ONCE 完成置 FINISHED）。

## 1. 触发源模型

- **FR-02-01** 三类触发源，统一进入同一执行入口（service 层单点）：

| 触发源 | 来源 | trigger_user 记录 |
|---|---|---|
| SCHEDULED（计划到点） | qcm 调度器 | `system` |
| MANUAL（立即执行） | 计划页「立即执行」按钮 | ruoyi 登录用户名（`SecurityUtils.getUsername()`） |
| REMOTE（远程触发） | SDK 调用方 | 调用方标识 sourceName（远程标记，如「xxx 系统」） |

- **FR-02-02** 触发源复用现有 `task_type` 列与 `TaskTypeEnum` 编码（AUTO=0 / MANUAL=1 / REMOTE=3；LIVE=2 保留现状不动），`trigger_user` 为新列（见 04 §3）。
- **FR-02-03** 执行链路沿用现有管线：触发 → 互斥检查 → 创建记录（批次）→ 组 flowParams（浓度 / 流量 / 时长覆盖）→ `composer.execute(execType, gas, params)` 异步 → 结果回调写库。现有 `EnvQualityControlTask` 执行、启动失败留痕（`persistAndWrapCalibrationLaunchFailure`，`tasks/EnvQualityControlTask.java:264-273`）、断电恢复（onStart 将运行中记录改失败）机制全部保留。

## 2. 单飞互斥与冲突留痕（D10）

- **FR-02-04** 执行器单飞互斥（composer `runningFlow` 单实例，`EnvCalibrationComposerIntegration.java:48`）：已有任务执行中时，任何新触发不启动第二个执行，按触发源分别处理如下，**三类都写执行记录**：
- **FR-02-05** 计划到点遇忙：该次触发写失败记录（每仪器一条，多仪器计划即 N 条同批次失败记录），failure_reason=`EXECUTOR_BUSY_CONFLICT`，trigger=SCHEDULED/`system`；ONCE 计划置 FINISHED；调度器照常重算下次。
- **FR-02-06** SDK 远程触发遇忙：同步返回 REJECTED（reason=BUSY_CONFLICT，附已写入的记录 id），同时写失败记录（每仪器一条），trigger=REMOTE/调用方标识（详见 03）。
- **FR-02-07** 手动立即执行遇忙：写失败记录（MANUAL/用户名），页面提示被拒原因（EXECUTOR_BUSY_CONFLICT + 当前正在执行的任务摘要）。
- **FR-02-08** 「远程任务正在执行中，本地计划任务到点」属 FR-02-05 的实例：冲突检测使后者失败并留痕（用户原始需求原文的落地）。反向（本地正在执行、远程触发进来）同理被拒。
- **FR-02-09** misfire（停机错过）与「忙冲突」严格区分：前者从未发生触发尝试，不写记录只日志（⚠️ OPEN-01）；后者是真实触发被拒，必须留痕。

## 3. 多仪器零点质控（新任务类型）

- **FR-02-10** 新类型（⚠️ OPEN-03 暂名 `MULTI_ZERO_CHECK` / className `air.monitor.calibration.multi_zero_check`）：一次执行 = N 台仪器（1~4，SO2/NOx/CO/O3 任选）**同时**进入零点检查（D4：同时启动，非逐台串行）。
- **FR-02-11** 参数模型：`instruments` 数组 + 零点类时长参数（§01 表）；无浓度、无标气流量（零点用零气）。
- **FR-02-12** 记录模型（D5）：一次执行产生 **N 条执行记录**（每台仪器一条），同 `batch_id`；每条记录结构复用单仪器零点记录（各自阶段时间线 phaseTimelines、各自监测数据与结果评定——零点漂移逐台计算）。
- **FR-02-13** 与旧「零点检查（单仪器）」类型共存（D4）：两者都出现在类型下拉；新计划默认引导用新类型（多选含单台）；旧类型保留供既有习惯与兼容路径。
- **FR-02-14** composer 接线前的中间态：composer 尚无该 ExecutorType flow，qcm 侧先建好类型 / 参数 / 记录模型；此时触发新类型 → 走现有启动失败留痕，failure_reason=`EXECUTOR_TYPE_NOT_READY`，不阻塞其他类型执行。composer 新 flow（一次 flow 内并行驱动 N 台仪器，保持 composer 单飞模型不破坏）为独立后续任务，本需求集只定义其对 qcm 的契约：**execute(instruments[], zero 参数) → 每台仪器一份阶段时间线与结果**。
- **FR-02-15** 报告生成对新类型的适配（每台仪器一份零点报告数据）为后续任务（D4 注明），本期报告生成范围不变。

## 4. 批次模型

- **FR-02-16** 每次触发（无论触发源、无论是否被拒）生成唯一 `batch_id`（UUID）；单仪器类型批次 = 1 条记录；多仪器零点 = N 条；冲突拒绝也构成批次（N 条失败记录同 batch_id）。
- **FR-02-17** 执行记录列表支持按批次分组展示（同批次记录相邻 / 可折叠，展开见各仪器记录）；批次内共享触发源 / 触发者 / 起始时间。
- **FR-02-18** 手动 / SDK 触发的返回值与后续查询都以 batch_id 为主键（详见 03）。

## 5. 终止

- **FR-02-19** 保留现有单条终止能力（`stopEnvQualityControlRecords`：状态置 STOPING → `executor.stop()` → 结果落库，`EnvQualityControlRecordsServiceImpl.java:128-160`）。
- **FR-02-20** 批次终止：多仪器零点批次中终止任一条 = 终止整个 flow → 批次内全部记录进入终止流程并落库终止状态（现有 `ExecutorStoppedException` 分支处理，`EnvQualityControlTask.java:445-470` 扩展到批次）。
- **FR-02-21** 终止权限沿用现有 records:stop 权限（见 05）；终止操作记 ruoyi 操作用户。

## 6. 执行记录的触发溯源字段

- **FR-02-22** 每条 `qcm_record` 必须可回答：谁触发（trigger_user）、何种途径（task_type=触发源）、哪一批（batch_id）、哪个计划（plan_id + 计划快照）、为何失败（failure_reason 结构化枚举，见 04 §3）。
- **FR-02-23** failure_reason 枚举（首期）：`EXECUTOR_BUSY_CONFLICT`（忙冲突）/ `EXECUTOR_TYPE_NOT_READY`（新类型未接线）/ 沿用现有启动失败、异常等文本路径（execution_log），结构化枚举仅覆盖新语义，不做全量重构。
