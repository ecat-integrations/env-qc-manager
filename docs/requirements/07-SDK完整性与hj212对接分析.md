## 二、hj212-sichuan 调研：它到底在干什么（事实 + 凑活定性）

### 2.1 机制事实

- **规则驱动**：四川平台下发规则配置（`rulesMap`：CN/Flag/ST/search_minute/rule_type，
  `Hj212ProtocolClient:77-79` 配置加载），质控组=规则 10006（`:158-161`），按时间窗
  （search_minute 切段/平台补数请求 startTime~endTime）要求上报。
- **现行走「实时」变体**：`searchPushQualityControlRealDatas`（`:391`；旧的按窗查报告版
  `searchPushQualityControlDatas` 在 `:390` 已被注释弃用）。每个上报窗口先
  `PostQualityControlGenReportTask(begin,end)` **触发 qcm 生成报告**（`SiChuanHj212DataService:690-694`），
  再 `getByDateRangeByCreateTime` 查报告（`:949`），解析 report_content JSON 映射 w50xx/w60xx 因子推送。
- **远程触发质控**：`handleQualityControlTask`（`Hj212ProtocolClient:688`，triggerType=3）——
  原始需求「远程标记」的现网实例，走旧 Task 通道、无受理/冲突返回。

### 2.2 数据需求的本质拆解（w50001~w60020 因子 → 数据本源）

| 因子组 | 现取自 report_content | **数据本源（实证）** |
|---|---|---|
| 标气来源/编号（w50001/02, w60001/02） | instrument_info.gas_source/gas_no | **报告生成时事后读钢瓶气设备**（`ReportGenerator:132-150` applyStandardGasSourceAndNoFromLogicDevices）——非执行时快照！ |
| 标气浓度/满量程（w50003/04） | instrument_info/full_span | 标气浓度=执行参数（浓度），满量程=设备量程 |
| 零/跨起止、响应浓度、标准浓度（w50005~14） | calibration_points | **qcm_record.execution_log**（阶段时间线+判定值） |
| 漂移量/校准结果（w50015/16/17） | zero/span_80_drift_result 等 | **execution_log.result**（resultValue/isPass） |
| 六浓度点/六响应/曲线 a·b·r（w60004~18） | gas_concentrations_input / instrument_responses / calibration_curve | **execution_log.result 的 stdValues[]/deviceValues[]/slope/intercept/correlation**（`GenMultiCheckReport:91-101` metricsForReport 实证——多点核查的 result 本身就是序列+曲线） |
| 校准日期（w50018/w60020） | instrument_info.report_date | 执行时间 |
| 关键运行参数（温度/流量/压力） | keyParameters（报告含） | **execution_log.keyParametersSnapshot** |

### 2.3 凑活定性（为什么说它是临时方案）

1. **四跳链**：执行 →（触发）生成人读报告 → 查报告表 → 解析人读 JSON → 映射因子。
   报告（qcm_report + ruoyi 页面 + 七类 D 表模板）是**给人看的展示层物化**，被当成机器接口用。
2. **机器契约脆弱**：report_content schema 由 7 个 Gen*Report 各自手拼（排版演进一步，hj212 的
   6 分支 ×18~20 因子映射就断）；补数依赖「报告已生成且未被废弃」。
3. **计量溯源缺失**：标气来源/编号在环境里无配置入口，报告里恒为气体名回退值/null
   （v2.1 实证，§4.2）——川标 w50001/02 上报出去就是空；且读取发生在报告生成时而非执行时，
   即使补了配置也无法回溯「执行当时用的是哪瓶」。

## 三、第一性原理分析

### 3.1 平台到底要什么（往深挖）

四川平台的规则下发+时间窗，本质是三个正交需求：

1. **质控执行的控制**（何时/何仪器/何参数执行一次质控——含平台远程发起）；
2. **质控活动的机器可读回溯**（补数/审核）：「某时间窗内发生过的每次质控活动，
   其**计量学事实**完整且不可篡改」——何时（时间线）、何仪器、用哪瓶标气（**溯源**）、
   过程数据（浓度点/响应/漂移）、判定结论、运行工况。
3. **按窗口重放**：时间窗不是「查报告」需求，是「该窗内发生的事件重放」需求——
   与报告是否生成无关（事件执行完即事实成立）。

### 3.2 事实中心 vs 报告中心

**执行事实（qcm_record.execution_log + 触发/溯源上下文）已包含机器所需的 ~95% 数据**——
判定明细、过程序列、曲线、阶段时间线、关键参数快照全部在（§2.2 实证）。
缺的只有两样：**标气溯源的配置面+执行时快照**、**仪器名称/编号的完成时冻结**（§4.0/§4.2）。

**报告是执行事实+设备快照的人读重组**。机器消费（hj212/未来的 LIMS/数采网关）的正确契约是
**执行事实**，不是报告。→ SDK 的数据面应该是「质控执行事实查询」，报告回归展示层。

## 四、更优解设计（执行事实中心）

### 4.0 SdkExecutionResult 是什么——命名、快照原则、结构与用法

**命名**：SDK 数据面核心 DTO 定名 `SdkExecutionResult`（一次质控执行的结果，通用、明确）；
过滤查询同名 `queryResults(filter)`、单条 `getExecutionResult(recordId)`。

**核心原则：完全快照独立保存，读时零关联（可溯源机制化）**

一次执行的结果在**执行完成时一次性冻结为完整快照**，消费时**只读快照、不做任何关联查询**
（不查设备注册表、不联计划表、不读钢瓶气配置、不反查任何 live 对象）。设备改名、计划编辑/
删除、钢瓶更换之后，历史结果永远保持「执行当时」的样子——溯源不依赖任何可变状态的存活。

快照分两个时刻，各自冻结当时的真相：
- **触发时**（record_snapshot）：计划配置快照（类型/仪器/浓度/流量/时长覆盖）；
- **完成时**（execution_log 一次性写入，即结果快照本体）：判定（含序列/曲线）、阶段时间线、
  关键参数、采样窗口、触发者、**仪器名称/编号（冻结当时值，现报告是生成时 live 读设备——升级点）**、
  标气溯源（§4.2 配置面补齐后纳入）、满量程。

**存储架构（v2.3：强类型结构化，禁 JSON 弱类型承载机器契约）**

标量→列、列表→子表、JSON 降级为归档；`SdkExecutionResult` 读强类型列/子表，**零 JSON 解析**：

```
qcm_record（完成时 UPDATE，同一事务）：
  ── 判定标量（激活原设计三列，旧实现绕开塞 JSON 导致恒 null）──
  standard_value=标气浓度  monitoring_data=仪器读数  calculated_value=漂移/计算值
  + check_pass_limit / check_calib_limit / is_pass / slope / intercept / correlation
  ── 快照层（完成时冻结，读时零关联）──
  + full_scale / instrument_name / instrument_no / gas_source / gas_no / gas_concentration
  + sampling_start_time / sampling_end_time
  ── 执行标识与 flow 关联（§4.0.1）──
  + trigger_request_id / flow_type / flow_execution_ref
qcm_record_phase     (record_id, seq, phase_code, phase_name, estimated_seconds, start_time, end_time)
qcm_record_key_param (record_id, seq, name, value, unit, ref_range)
qcm_record_point     (record_id, seq, std_value, device_value)  ← 多点/精密度序列
execution_log        保留为原始归档（排障/人读/凭证），机器契约不再读它
```

#### 4.0.1 执行标识与 flow 关联（现状缺口 → 全新设计）

**现状实证（2026-08-23 核查）**：
- flow **类型**有列：`quality_control_type`（NOT NULL）与 composer ExecutorType/Flow 类 1:1 映射 ✓；
- flow **执行实例 ID 不存在**：`AbstractCalibrationFlow` 实例字段仅 ctx/gas/phaseManager/stopped/runningFuture
  （无 id），`ExecutorResultBase` 亦无；qcm 侧关联是纯内存临时态——`executorMap.put(recordId, flow)`
  运行中存在、完成即删，**不落库**；排障只能靠时间戳人工对齐 composer 日志；
- 存量数据一致性问题：`quality_control_type` 实际存了枚举 **code `'1'`** 而注释声明 **name**
  （`span_check`）——写入路径与注释不一致。

**设计原则**：执行 ID 的事实源在 qcm（执行事实主体），不在 composer（无状态单飞引擎）——
不给 composer 发明实例 ID，而是把 qcm 自身执行标识链补全、把关联冻结进记录：

| 层 | 标识 | 状态 |
|---|---|---|
| 仪器级执行 | `record.id` | 已有（事实 ID 本体） |
| 触发批次 | `batch_id` | 已有（N 仪器共享一次触发） |
| 触发请求 | `trigger_request_id` **新增**：trigger 受理时生成并返回调用方，逐 record 落库——外部全程对账（SDK 受理→轮询→结果三段同一标识） | 新增 |
| 执行体类型 | `flow_type` **新增**：冗余冻结 composer ExecutorType className（如 `air.monitor.calibration.span_check`）——qc_type 是业务枚举、flow 类名是引擎实现，两者映射今天 1:1 将来未必；快照原则要求冻结「当时跑的是什么执行体」 | 新增 |
| 排障关联 | `flow_execution_ref` **新增**：编排器启动执行时生成（`recordId@startMillis`），传入 composer 作 correlation 标识打日志（composer 仅加透传日志字段、不引入状态），同时落库——composer 日志行从此可机器关联回 record | 新增 |

**顺带规范化**：`quality_control_type` 统一存 name（写入路径+注释对齐；全新设计不考虑旧数据兼容，
存量 dev 行随重灌/不理）。

- 关键正当性：三列是**原表设计（D18 长期验证）本有的强类型列**，旧实现弃用塞 JSON——本方案是回归原设计意图；
- 收益：DB 约束兜底（类型/非空）、可索引可筛选（按 is_pass/仪器补数）、单位错位类缺陷（G-BUG-20）
  在强类型层无所遁形；代价：DDL+mapper+写入路径改造量高于「JSON 原地扩」——结构化的正常成本。

**结构（五层，全部来自快照，读路径零 live 查询）**：

| 层 | 字段 | 快照来源（何时冻结） | 外部拿来做什么 |
|---|---|---|---|
| 事件层 | recordId, batchId, planId, qcType, instrument, triggerSource, triggerUser, startTime/endTime, executionStatus(+Name), failureReason | qcm_record 列（触发/完成时） | 事件定位/补数去重/审计 |
| 过程层 | phaseTimelines[] | execution_log.qcPhaseTimelines（完成时） | w50005/06/11/12 起止时间 |
| 判定层 | judgement{ resultValue, stdValue, deviceValue, checkPassLimit, checkCalibLimit, pass, stdValues[], deviceValues[], slope, intercept, correlation } | execution_log.result（完成时；多点序列与曲线键原生就在） | w50013~17、w60004~18 全部数值因子 |
| 工况+溯源层 | keyParameters[], samplingWindow, instrumentName/instrumentNo, gasSource/gasNo/gasConcentration, fullScale | keyParametersSnapshot（完成时）；instrumentName/No 与标气溯源、满量程为**新增冻结项**（完成时写入，§4.2） | w50001~04 标气溯源、w50018、仪器识别 |
| 结论层 | resultEvaluation | qcm_record（完成时） | 兜底人读 |

**外部使用方式**（hj212 例——只读结果对象，无任何关联查询）：

```java
// 补数/上报窗口：一查一映射，不碰报告、不碰设备
for (SdkExecutionResult r : sdk.queryResults(filter)) {
    Judgement j = r.getJudgement();
    if ("span_check".equals(r.getQcType())) {
        push("w50005", r.getPhaseStart("check"));       // 过程层（快照）
        push("w50014", j.getDeviceValue());             // 判定层（快照）
        push("w50017", j.isPass() ? 0 : 1);
        push("w50001", r.getGasSource());               // 溯源层（执行当时快照；配置面补齐前 null 如实上报）
        push("w50018", r.getInstrumentNo());            // 仪器编号（执行当时冻结，改不受影响）
    } else if ("multi_check".equals(r.getQcType())) {
        for (int i = 0; i < j.getStdValues().size(); i++) {
            push("w60004_" + i, j.getStdValues().get(i));
            push("w60010_" + i, j.getDeviceValues().get(i));
        }
        push("w60018", j.getCorrelation());
    }
}
```

### 4.1 SDK 数据面 = 执行事实查询（替代 v1 的「报告透传」路线）

```
QualityControlSdk（控制面已有：trigger 受理/冲突/allowQueue —— 保持不变）
  ├─ queryResults(ResultFilter)          // 时间窗/仪器/类型/触发源/批次 → List<SdkExecutionResult>（只读快照）
  └─ getExecutionResult(recordId)        // 单条同构（原 getRecordDetail 升级，读时零关联）
```

- **多点/精密度/准确度的序列与曲线**来自 result Map 原生键（stdValues/deviceValues/slope…），
  不需要任何新落库——第一性验证过（§2.2）。
- **queryResults 即补数**：结果快照随执行完成落库，不依赖报告生成任务跑过；读路径零 live 查询。

### 4.2 标气溯源：先补配置面，再执行时快照（v2.1 修正，用户实证纠偏）

**实证（2026-08-23，用户指误后核查）**：报告里标气信息实际是**空的**——三行报告
`gas_source` 均为气体名回退值（"SO2"）、`gas_no` 恒 null；钢瓶气逻辑设备上**不存在**
「来源/编号」属性（gas_setting 实证仅三个「XX标气浓度」属性），
`tryReadStandardGasSourceAndNo` 按显示名模糊扫描恒落空。v2 原文「执行后换瓶污染历史」
的场景当前不成立——**真缺口是配置面从未存在**。连带疑点：钢瓶 SO2 浓度=50.00 **ppm**，
报告 instrument_info 写 `"50.00 ppb"`（数值原样、单位错位 1000 倍，待修时一并核）。

修正后三步——**已实施并升级为方案 A 终态**（2026-08-24 用户定案：废 qcm_gas_info 自建表，
档案归一 airstation；见验收记录 change-batch-20260824-archive-unification）：
1. **配置面**：真相源=airstation `logicdevice_station.standard_gas.{so2|nox|co}` 槽的 standalone
   属性 `gas_source`（本批新增，默认「未设置」）/ `cylinder_id` / `gas_concentration`（元数据补齐，
   与瓶号同机制）；GasSetting 弹窗=换瓶登记，转写设备属性（qcm 不落自有表）；
2. **执行时快照**：完成时读档案 AttrState 一次，冻结进 `qcm_record.gas_source/gas_no/
   gas_concentration/gas_concentration_unit`（强类型列）。**槽映射**：qcm 数字代码→槽
   （1→so2 / 2→nox（NOx 分析仪用 NO 标气，用户定案）/ 4→co / 3(O3)→无槽如实空）；
   属性无状态快照（从未写入）=未登记语义，字段 null（G-BUG-23 曾因此 NPE 炸失败留痕）；
3. **消费同源**：报告生成与 SDK SdkExecutionResult 均读快照冻结列（报告侧保留模糊扫描
   仅作旧记录回退，新记录一律命中冻结列）。配置完成前 w50001/02 如实空值上报（不伪造）。
   快照隔离已实证：record 16 冻 GBW-E-060522 / record 17 冻 GBW-E-860823（两次执行间经浏览器换编号，历史不受影响）。
